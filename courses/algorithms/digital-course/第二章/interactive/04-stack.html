一、栈帧到底装了什么

Stack Frame · 三大字段
定义 2.5 · 栈帧

函数每被调用一次，系统就在运行时栈（run-time stack，又称系统栈）的栈顶分配一块连续存储区，称为该次调用的栈帧（stack frame）或活动记录（activation record）。函数返回时该栈帧被弹出。栈帧使得同一个函数的多次调用互不干扰——这正是递归得以成立的物理基础。

上方动画中每一个方块，实际上都是下表这样一个三段结构。动画为简洁只画了 fact(n) 这一行文字，请对照下表理解方块内部真实的内容。
#字段存的是什么为什么必须保存fact(3) 那一帧的取值
① 实参
parameters		 本次调用收到的参数值的副本 每层的 n 各不相同。若只有一份 n，fact(3) 递归进 fact(2) 时 n 会被改写，回溯时就乘错数。每层独立一份是递归正确性的前提。 n = 3
② 返回地址
return address		 调用发生时下一条待执行指令的地址 子调用结束后 CPU 必须知道"回到哪儿继续"。fact(3) 在 return n*fact(2) 处暂停，返回地址就指向"拿到结果后做乘法"那条指令。 指向 fact(4) 体内的乘法指令
③ 局部变量
local variables		 函数体内定义的变量、中间结果、需保护的寄存器 同样每层一份。若函数体里有 int half = power(a,n/2);，这个 half 必须在本层保存，等子调用回来后使用。 （fact 无局部变量，为空）
执行 fact(4) 触底瞬间，系统栈的真实样貌（栈顶在上）： ┌──────────────────────────────┐ ← 栈顶 top / 当前活动帧 │ fact(0) ① n=0 ② 回 fact(1) ③ — │ ├──────────────────────────────┤ │ fact(1) ① n=1 ② 回 fact(2) ③ — │ ├──────────────────────────────┤ │ fact(2) ① n=2 ② 回 fact(3) ③ — │ ├──────────────────────────────┤ │ fact(3) ① n=3 ② 回 fact(4) ③ — │ ├──────────────────────────────┤ │ fact(4) ① n=4 ② 回 main ③ — │ ├──────────────────────────────┤ │ main … │ ← 栈底 bottom └──────────────────────────────┘ 此刻栈中共 5 个 fact 栈帧，即最大递归深度 = n + 1 = 5。
两个阶段：递归执行分为递推（下降）与回溯（返回）两个阶段。递推阶段不断压栈（push），栈越来越高，直到触及递归出口；回溯阶段不断弹栈（pop），每弹一层就用返回地址回到上层、把返回值代入上层的表达式继续算。动画中"栈越堆越高再逐层消失"演示的就是这两个阶段。

二、空间复杂度：递归深度决定一切

S(n) = O(最大递归深度)
定理 2.1 · 递归算法的空间复杂度

设递归算法执行过程中最大递归深度为 d(n)，单个栈帧大小为常量 c，且算法未使用与 n 相关的额外数据结构，则其空间复杂度为
S(n) = c · d(n) = O( d(n) )。
即：栈帧数 = 当前递归深度，空间复杂度 = 最大递归深度（而不是总调用次数！）。

S(n) = O( 最大递归深度 d(n) )　　≠　O( 总调用次数 )
为什么不是"总调用次数"？因为栈帧用完就弹出，同一时刻栈上只有当前这条根到叶的路径上的帧。Fib(n) 朴素递归总共调用约 1.618n 次，但任一时刻栈里最多只有 n 层——所以它时间 Θ(1.618n) 而空间只有 Θ(n)。时间数结点，空间数树高（见 §05 递归树）。

三、栈溢出：多深会炸，怎么避免

Stack Overflow · 边界估算
定义 · 栈溢出

当程序请求的栈空间超过系统为该线程预留的栈区上限时，栈指针越过栈边界，触发栈溢出（stack overflow）。操作系统检测到访问保护页后立即终止进程：Linux 报 Segmentation fault（信号 SIGSEGV），Windows 报 0xC00000FD STATUS_STACK_OVERFLOW。

最大安全递归深度的估算公式： dmax ≈ 栈容量 ÷ 单帧大小 典型栈容量：Linux 主线程默认 8 MB（ulimit -s 查看，常见 8192 KB） 　　　　　　Windows 主线程默认 1 MB 　　　　　　新建线程默认 1~2 MB；嵌入式系统可能仅几 KB 典型单帧：简单函数（1~2 个 int 参数）约 32~64 B 　　　　　含大局部数组的函数可达 KB 甚至 MB 级 ⇒ Windows 1 MB / 48 B ≈ 2 万层 ⇒ Linux　 8 MB / 48 B ≈ 17 万层 ⇒ 若函数里有 int buf[1000];（4 KB/帧）：8 MB / 4 KB ≈ 2000 层就炸
工程经验值：不带大局部变量的简单递归，深度 ≤ 104 基本安全，104~105 视平台而定（Windows 上常已危险），> 105 应当假定会溢出。设计算法时必须先估算 d(n)：n=106 的链表用递归遍历一定崩，而 n=106 的平衡树只需 20 层，完全安全。
规避手段做法效果代价 / 限制
① 改迭代（首选）单链递归改 while；多分支递归用显式栈栈深降到 O(1)；显式栈开在堆上，容量可达 GB代码变长、易错
② 尾递归 + 编译优化引入累加器改成尾递归，编译时加 -O2编译器复用栈帧，栈深 O(1)C++ 不保证；-O0 下无效（见 §02）
③ 减小递归深度把"规模减 1"改成"规模折半"（分治）d(n) 从 n 降到 log n需要问题本身支持折半
④ 增大栈容量Linux ulimit -s unlimited；链接选项 -Wl,--stack,268435456；新建大栈线程临时救急，可撑到百万层治标不治本，且部分评测环境禁用
⑤ 减小单帧把大局部数组改成 static 或全局；少传值多传引用/指针单帧从 KB 降到几十 B，深度提升上百倍需注意 static 破坏可重入性

四、递归改迭代：显式栈模拟

Explicit Stack Simulation
核心思想：递归之所以能工作，是编译器替你维护了一个栈。既然如此，我们完全可以自己声明一个 stack 容器，把原本由栈帧保存的"实参 + 执行进度"手工存进去，用一个 while 循环反复取出处理。这样系统栈深度恒为 O(1)，而数据栈开在堆上，不受 1 MB 限制。
1
确定要保存什么：原递归函数的参数，以及"这一层执行到第几步"的状态标记（若递归调用后还有后续动作）。
2
初始化：把最外层调用的参数压入自建栈。
3
主循环：栈非空时弹出栈顶，做本层 O(1) 工作，再把子问题参数压栈（注意压栈顺序与期望处理顺序相反）。
4
处理返回值：若原递归需要子问题的返回值（如 fact 的乘法），则需在栈中额外保存"待合并的中间结果"，或改用自底向上的循环直接算。
// ===== 情形 A：无返回值依赖（先序遍历）—— 直接压栈即可 ===== void preorderIter(Node *root) { if (!root) return; stack<Node*> st; // 自建栈，位于堆上 st.push(root); while (!st.empty()) { Node *p = st.top(); st.pop(); visit(p); if (p->right) st.push(p->right); // 先压右 if (p->left) st.push(p->left); // 后压左 ⇒ 左先出栈 } } // ===== 情形 B：有返回值依赖（阶乘）—— 需保存中间结果 ===== // B1. 显式栈版：先把所有 n 压进去，再逐个弹出相乘（模拟回溯阶段） long long factStack(int n) { stack<int> st; for (int k = n; k > 0; --k) st.push(k); // 递推阶段 long long res = 1; while (!st.empty()) { // 回溯阶段 res *= st.top(); st.pop(); } return res; } // B2. 其实此例乘法可交换，栈完全多余，直接循环即可（空间 O(1)） long long factLoop(int n) { long long res = 1; for (int k = 2; k <= n; ++k) res *= k; return res; }

注意区分"省空间"和"换地方"：显式栈并没有把空间需求变小（仍是 O(n)），它只是把这 O(n) 从容量很小的系统栈挪到了容量很大的堆上。真正把空间降到 O(1) 的是纯循环改写，但这只在递归结构足够简单（单链、且合并运算可交换/可累积）时才办得到。
易错点
  • 把空间复杂度算成"总调用次数"。Fib 朴素递归调用 Θ(1.618n) 次，但空间只有 Θ(n)——栈帧弹出后就释放了。时间数结点数，空间数树的高度。
  • 认为"递归没 new 过内存所以空间 O(1)"。栈帧是隐式开销，同样计入空间复杂度。这是本章最高频的错误。
  • 忽略单帧大小。在递归函数里写 int buf[1000];，单帧 4 KB，8 MB 栈只够 2000 层。大数组绝不要放在递归函数的局部变量里，改成全局/static/传引用。
  • 以为记忆化能解决栈溢出。记忆化把时间从指数降到多项式，但递归深度不变（Fib 记忆化后深度仍是 n）。栈溢出要靠改迭代/减深度，不是靠记忆化。
  • 显式栈的压栈顺序搞反。栈是 LIFO，希望先处理左子树就必须后压左子树。写成"先压左后压右"会得到"根右左"序。
  • 用 ulimit -s unlimited 当作正式解决方案。它只在本机生效，评测机、生产环境、其他线程都不吃这一套；且掩盖了算法本身深度过大的设计缺陷。
  • 误以为迭代版一定更快。显式栈的 push/pop 也有开销，有时比编译器高度优化过的栈帧操作还慢。改迭代的首要理由是避免溢出，不是提速。
本节小结
  • 栈帧三大字段：① 实参（每层独立一份，保证各层互不干扰）② 返回地址（告诉 CPU 子调用结束后回哪继续）③ 局部变量（含中间结果与被保护的寄存器）。栈帧是递归能够成立的物理基础。
  • 递归执行分递推（压栈）与回溯（弹栈）两阶段；fact(4) 触底时栈中同时有 5 个栈帧。
  • 定理：S(n) = O(最大递归深度)，不是 O(总调用次数)。Fib 朴素递归时间 Θ(1.618n) 而空间仅 Θ(n)，就是最好的说明。
  • 栈溢出边界：dmax ≈ 栈容量 ÷ 单帧大小。Windows 1 MB ≈ 2 万层，Linux 8 MB ≈ 17 万层；深度 > 105 应假定会溢出。
  • 五种规避手段：改迭代（首选）、尾递归 + -O2、减小递归深度（减 1 → 折半）、增大栈容量（治标）、减小单帧（大数组移出局部变量）。
  • 显式栈模拟把编译器维护的栈手工重建在堆上：系统栈深降为 O(1)，额外空间仍是 O(n)——是换地方而非省空间。
1朴素递归 fib(n) 的时间复杂度约为 Θ(1.618n)，那么它的空间复杂度是？
AΘ(1.618n)，因为每次调用都要一个栈帧
BΘ(n)
CΘ(log n)
DΘ(1)，因为函数里没有申请任何数组
解析：选 B。
A 是最典型的陷阱：栈帧确实每次调用都要一个，但它用完立刻弹出。同一时刻栈上只有"从根到当前结点这一条路径"上的帧，而 fib 递归树的高度是 n（最左那条链 n→n−1→…→0），故空间 Θ(n)。
C 错：n 每次只减 1 或 2，不是折半，没有 log。
D 错：栈帧是隐式空间开销，必须计入。
口诀：时间数递归树的结点数，空间数递归树的高度。
2某递归函数体内声明了 int buf[2048];（约 8 KB），运行在 8 MB 栈上。它大约能安全递归多少层？
A约 17 万层，和普通递归函数一样，因为局部数组不占栈
B约 8 万层
C约 1000 层
D无限层，只要不写死循环就不会溢出
解析：选 C。dmax ≈ 栈容量 ÷ 单帧大小 = 8 MB ÷ 8 KB = 1024 层左右。
A 严重错误：局部数组恰恰分配在栈帧里（非 static、非 new），是单帧膨胀的头号元凶，它让安全深度从十几万层暴跌到一千层。
B 错：8 MB/8 KB = 1024，不是 8 万。
D 错：栈容量有硬上限。
实践建议：递归函数内避免大局部数组，改成全局数组、static，或用指针/引用传入。
3把一个深度为 n 的递归改写成"显式栈 + while 循环"的迭代版后，空间复杂度会怎样变化？
A从 O(n) 降为 O(1)，因为不再使用系统栈了
B渐进阶仍是 O(n)，但从系统栈转移到了堆，从而绕开 1~8 MB 的栈上限
C升为 O(n2)，因为既有系统栈又有自建栈
D不确定，取决于编译器是否开启 -O2
解析：选 B。这是本节最需要澄清的一点：显式栈是换地方而非省空间。你仍然要存 n 份"待处理的参数"，渐进空间依旧 O(n)；但 std::stack 的元素分配在堆上，堆通常可用 GB 级内存，而线程栈只有 1~8 MB，因此 106 层不再溢出。
A 错：只有把递归改成纯循环（不需要保存历史状态，如 factLoop）才能真正做到 O(1)。
C 错：系统栈此时深度是 O(1)，两者不相乘。
D 错：-O2 影响的是尾递归优化，与显式栈改写无关。
