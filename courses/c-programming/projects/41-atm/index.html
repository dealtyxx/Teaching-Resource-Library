嵌套结构体业务流程状态管理

场景导入：复杂业务的两根支柱

ATM 看似简单，实则是”复杂业务系统”的微缩模型。拆开看只有两根支柱：

  • 结构体管数据：账户嵌套卡片（Account 含 BankCard），从属关系直译成嵌套——acct.card.locked；
  • 状态机管流程：enum AtmState 定义”现在处于哪一步”，switch 决定”此刻允许做什么”。待机时不能取款、验密没过不能进菜单——把”不允许”写死在状态里，比在每处操作前打补丁可靠得多。

再叠加你的老朋友：验密三次锁卡（项目 16）、先查余额后扣款（项目 7 的先防护后操作）、strcmp 比密码（项目 29）。

atm.c（随状态实时生成）
#include <stdio.h>
#include <string.h>

typedef struct {          /* 嵌套:卡片信息 */
    char card_no[20];
    char pin[8];
    int  locked;
} BankCard;

typedef struct {          /* 账户:卡+余额 */
    char     holder[16];
    BankCard card;        /* 结构体嵌套 */
    int      balance;
} Account;

typedef enum { IDLE, PIN_CHECK,
               MENU, DONE } AtmState;

int main(void) {
    Account acct = {
        .holder = "Zhang San",
        .card = { "6217..8801", "1234", 0 },
        .balance = 3600
    };
    AtmState st = IDLE;
    /* 状态机主循环:switch驱动状态流转 */
    /* IDLE --插卡--> PIN_CHECK
       PIN_CHECK --strcmp==0--> MENU
       PIN_CHECK --3次失败--> 锁卡回IDLE
       MENU --取款: acct.balance -= amt
       MENU --退卡--> DONE --> IDLE  */
    return 0;
}

💡 复杂业务 = 状态机管流程 + 结构体管数据：enum 定义"现在处于哪一步"， switch 决定"此刻允许做什么"（待机时不能取款！），嵌套结构体承载"账户-卡片"的从属关系。 验密三次锁卡是项目 16 的 do-while 逻辑重生；先查余额后扣款是项目 7 的"先防护后操作"。 旧知识不断被新场景征用——这就是体系。

VibeCoding 三段迭代提示

  1. 手写基础版：实现”插卡→验密（3次机会）→取款→退卡”主循环。先画状态迁移图：4 个状态、每条箭头标注触发条件。
  2. AI 优化进阶版：让 AI 增加”转账”功能（两个 Account 之间）。审查关键点：转出方扣款和转入方入账必须同时成功或同时失败——AI 有没有意识到”转出成功转入失败”会凭空蒸发钱？（事务性思维的启蒙。）
  3. 信创加固定稿版：金额用”分”存储（int）而非”元”（float）——第 3 章”金融用整数”策略的正式落地；每笔操作追加日志记录（谁、何时、多少、余额）；取款限额与当日累计（新成员 + 新校验）。

素养与思政

你在 ATM 上取过的每一笔钱，背后都有一套绝不含糊的代码：状态不对不动账、余额不足不吐钞、三次错密即锁卡。金融软件的浪漫，是万无一失的无聊。 中国的银行核心系统正在经历国产化替换——数据库、中间件、操作系统逐层替代。替代的门槛不是功能（功能好抄），是几十年沉淀的严谨：每个边界条件、每条异常路径都被真金白银验证过。你今天写的双重校验，就是这种严谨的第一课。
