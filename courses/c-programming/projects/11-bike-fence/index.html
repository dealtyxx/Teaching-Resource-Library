共享单车电子围栏判定

综合挑战 北斗+生活 ★★★★ 约 120 分钟

学习目标：综合运用分支结构解决场景问题

嵌套分支边界条件逻辑组合

场景导入：还车键按下的那 0.1 秒

你骑共享单车到目的地，按下”还车”——App 在 0.1 秒内完成了一次判定：这辆车现在停在哪儿？能不能还？ 判定的依据是车载北斗模块报告的经纬度，规则是模块二所有知识点的总和：

  • 矩形围栏判定：lon >= 西边界 && lon <= 东边界 && lat >= 南边界 && lat <= 北边界——四个关系运算 + 三个 &&（复合条件）；
  • 嵌套结构：先判”在不在运营区”（外层），在运营区内再判”是不是禁停区”（内层）；
  • 边界条件：恰好压在围栏线上算里还是算外？>= 与 > 的一字之差，决定用户要不要付调度费。

这正是”北斗+生活”的意义：模块一你换算过北斗经纬度，现在这些坐标真正参与业务决策了。

main.c
1#include <stdio.h>
2/* 运营区围栏(由北斗定位坐标界定) */
3#define FN_W 116.312
4#define FN_E 116.408
5#define FN_S 39.869
6#define FN_N 39.931
7/* 教学楼禁停区 */
8#define NP_W 116.345
9#define NP_E 116.375
10#define NP_S 39.891
11#define NP_N 39.912
12 
13int main(void) {
14    double lon = 116.3585, lat = 39.9031;  /* 单车北斗坐标 */
15    if (lon >= FN_W && lon <= FN_E &&
16        lat >= FN_S && lat <= FN_N) {    /* 外层:在运营区? */
17        if (lon >= NP_W && lon <= NP_E &&
18            lat >= NP_S && lat <= NP_N) { /* 内层:在禁停区? */
19            printf("禁停区:禁止还车,请移出\n");
20        } else {
21            printf("围栏内:还车成功,行程结算\n");
22        }
23    } else {
24        printf("运营区外:无法还车,持续计费\n");
25    }
26    return 0;
27}

💡 这就是真实共享单车 App 的核心判定逻辑：北斗/GPS 坐标 + 嵌套矩形判断。 先判"在不在运营区"（外层），再判"在不在禁停区"（内层）—— 顺序反过来行不行？想想校外恰好与禁停区经度重叠的点会发生什么。

VibeCoding 三段迭代提示

  1. 手写基础版：写死围栏坐标，读入单车经纬度，输出三种判定之一。先在纸上画出两个矩形和三种区域。
  2. AI 优化进阶版：让 AI 增加第二个禁停区（图书馆），并输出距离最近可停区边界的粗略方位提示（东/南/西/北）。审查它的嵌套层次：三层 if 还清晰吗？要不要用标志变量拆解？
  3. 信创加固定稿版：所有边界坐标宏定义并注明”压线算内”（>=）；增加坐标合法性外层防护（经度 -180180、纬度 -9090，第 3 章的范围校验回来了）；思考若北斗信号漂移 ±10 米，边界判定要不要加”缓冲带”？
