分布式光伏站点台账管理

进阶选做 信创场景 ★★★★★ 约 130 分钟

学习目标：新能源场站数据架构设计

结构体数组增删改查数据台账

场景导入：CRUD——信息系统的四个原子动作

县里的分布式光伏台账：村委屋顶、小学车棚、养殖场大棚……每个站点一条记录。运维每天在做四件事：增（新站并网）、删（站点注销）、改（离线标记）、查（按 ID 找站）。

这四个动作合称 CRUD，是从学籍系统到 12306 的一切信息系统的骨架。C 语言的最小实现 = 结构体数组 + 计数器：

Station ledger[CAP];   /* 固定容量的"账本" */
int     count = 0;     /* 当前有效条数 */

四个动作各有一个必须想清楚的细节：增要查满（count 到顶拒绝）；删要搬移（后续记录整体前移补洞）；查要处理找不到（返回 -1）；改要先查后写（find 到下标再动成员）。

台账 = 结构体数组 + 计数器 count。试试增删改查四个操作。
pv_ledger.c
#include <stdio.h>
#include <string.h>
#define CAP 8

typedef struct {
    char id[8]; char owner[20];
    int  kw; int kwh_today; int online;
} Station;

Station ledger[CAP];   /* 台账本体 */
int     count = 4;        /* 有效条数 */

int add(Station s) {              /* 增 */
    if (count >= CAP) return -1;  /* 满则拒绝 */
    ledger[count++] = s;          /* 结构体整体赋值 */
    return 0;
}
int del(int i) {                  /* 删 */
    if (i < 0 || i >= count) return -1;
    memmove(&ledger[i], &ledger[i+1],
            (count-1-i) * sizeof(Station));
    count--;                      /* 后续整体前移 */
    return 0;
}
int find(const char *id) {        /* 查 */
    for (int i = 0; i < count; i++)
        if (strcmp(ledger[i].id, id) == 0)
            return i;             /* 返回下标 */
    return -1;
}
/* 改 = find + 直接写成员:
   int i = find("PV-102");
   if (i >= 0) ledger[i].online = 0;  */

💡 增删改查（CRUD）是一切信息系统的骨架——学籍系统、图书馆、12306 本质都是它。 注意"删"的成本：删 ledger[0] 要整体搬移后面所有记录（memmove）——数组的删除是 O(n) 的。 记录多到百万条怎么办？这个痛点正是第 11 章链表与动态内存出场的理由。

VibeCoding 三段迭代提示

  1. 手写基础版：实现 add/del/find 三个函数 + main 菜单循环（项目 16 的 do-while 菜单回归）。自检：增满了会怎样？删不存在的下标会怎样？
  2. AI 优化进阶版：让 AI 增加”按容量排序输出报表”（复用项目 38）与”总装机/在线率统计”（复用项目 14 三大件）。审查它遍历是 i < count 还是 i < CAP——后者会把残留垃圾统计进去！
  3. 信创加固定稿版：ID 唯一性检查（add 前先 find，重复拒绝）；删除改”软删除”（加 deleted 标志，审计需要——金融/能源行业的合规常识）；对比软硬删除各自的代价。

素养与思政

截至 2024 年，全国分布式光伏装机超过 3.7 亿千瓦，其中很大一部分来自农村屋顶——“整县推进”让阳光成了农民的存折。每个县的调度中心里，都有一本这样的台账：谁并网了、谁离线了、今天发了多少度。 台账的严谨=收益的公正：漏记一条，就是一户人家的电费损失。CRUD 写得对不对，从来不只是技术问题。
