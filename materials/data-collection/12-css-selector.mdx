## 动手实验

换上 lxml 解析器，到底快多少？别猜——跑 200 轮计时，让数据自己说话：

<PyPlayground
  client:visible
  title="html.parser vs lxml：200 轮实测计时"
  packages={['beautifulsoup4', 'lxml']}
  note="把 ROUNDS 改成 500，或把 html 复制几倍变成更大的页面，看两者差距如何变化——结论必须跟着数据走。"
  code={`from bs4 import BeautifulSoup
import time

# 内联一段商品列表页面（重复 8 次模拟较大文档）
card = "<div class='item'><a href='/g'><span class='price'>Y58</span></a></div>"
html = "<html><body>" + card * 8 + "</body></html>"

ROUNDS = 200

def bench(parser):
    """用指定解析器跑 ROUNDS 轮「建树 + select」，返回耗时（毫秒）"""
    t0 = time.perf_counter()
    for _ in range(ROUNDS):
        soup = BeautifulSoup(html, parser)
        soup.select("div.item > a > span.price")
    return (time.perf_counter() - t0) * 1000

t_std = bench("html.parser")
t_lxml = bench("lxml")

print(f"html.parser : {t_std:7.1f} ms")
print(f"lxml        : {t_lxml:7.1f} ms")
print(f"速度比     : lxml 约为 html.parser 的 {t_std / t_lxml:.1f} 倍")
print()
print("结论只认数据：换解析器前先实测，别把「听说很快」写进技术选型报告。")`}
/>

## 思政会客厅

<DimCard dim="科研诚信" title="性能结论必须来自实测">
  <ul>
    <li>「lxml 更快」是社区共识，但写进你的选型报告之前，要有自己机器上的计时数据——引用结论和验证结论是两种职业习惯。</li>
    <li>基准测试要控制变量：同一文档、同一选择器、足够轮次，否则数据本身就是造假。</li>
    <li>把 perf_counter 用成肌肉记忆：可复现的数字，是工程师之间最硬的通货。</li>
  </ul>
</DimCard>

<DimCard dim="创新思维" title="表达力就是生产力">
  <ul>
    <li>CSS 选择器把「三层 find_all 嵌套」压缩成一行声明——学会站在更高的抽象层写代码。</li>
    <li>选择器语法与前端通用：一次学习，浏览器 DevTools、爬虫、自动化测试三处受益。</li>
    <li>工具在演进（html.parser → lxml → 更快的解析器），但「先量化再选择」的方法论不过时。</li>
  </ul>
</DimCard>
